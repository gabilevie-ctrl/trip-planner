# Live Plan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** "Choose" on a live option card asks Claude for a full plan, and the app shows that plan's days, bookings, totals, to-dos, gear (one column per traveller) and sources in the existing tabs, with a plan chat that changes it.

**Architecture:**
- Claude writes the plan through two strict tools, `write_plan` and `update_plan`.
- A pure module `src/liveplan.js` cleans that input, merges it by id while keeping what people edited, and computes totals and the to-do list.
- One view module, `src/views/liveplan.js`, renders the cards. Build, Itinerary, Plan & book, Money, Decisions and Share use those cards when the chosen destination is a live option; library destinations keep today's views.

**Tech Stack:** vanilla ES modules, Pico CSS, `node --test` with jsdom. No new library.

**Spec:** `docs/superpowers/specs/2026-11-09-live-planning-design.md`, stage 3 ("Live plan"), requirements 1, 3, 6 and 9, and "How it works for a person" steps 4–5.

## Global Constraints
- No framework, no bundler, no new vendored library in this stage.
- Live fetches only to `api.anthropic.com`, and only through `src/claude.js` with the unlocked key. Without the password the app still works: choosing an option sets it, and the plan cards say "Unlock live search in Setup to get the plan".
- Every number shown has a source. Totals, per-person figures and the to-do order are computed by `src/liveplan.js`, never written by Claude. A price with no rate to the trip currency is listed as missing and left out of the total, never guessed.
- Views return HTML strings. Interaction goes through `data-act`, `data-bind`, `data-form` in `src/main.js`. Every value from Claude or from a share link goes through `esc`; links must be `https:`.
- Traveller limits are flags, never silent exclusion.
- Hash routes stay plain names; no new route is needed (`#build`, `#itinerary`, `#plan`, `#money`).
- Trip shape changes: update `docs/DATA-MODEL.md` and `state.migrate()`. `scripts/validate.cjs` checks destinations only, so it needs no change.
- Only the current plan is shared. The last 3 replaced plans stay on the device in `trip._local.planHistory`, which share links strip.
- Model and settings as today (`claude-opus-5-5`, adaptive thinking, effort medium, web search `max_uses: 5`). Plan turns use `max_tokens: 32000`; option turns keep 16000.

## Decisions recorded here
These are deviations from the spec, or calls the spec left open.
- **`update_plan` replaces whole collections, merged by id.** The spec says "`update_plan` edits by id". Its input has the same keys as `write_plan`, each nullable. A non-null collection replaces that collection, and items are matched by id. A per-field patch language does not fit a strict schema with one shape per collection. The cost is more output tokens on a change.
- **Claude chooses readable ids** with a fixed prefix per collection: `d_` day, `l_` leg, `b_` booking, `p_` permit, `a_` admin item, `g_` gear, `t_` to-do, `c_` other cost. Days and legs refer to bookings by those ids. The app enforces the prefix and uniqueness, and makes a fresh `uid` when an id is bad.
- **People own these fields; Claude can't overwrite them on an item that already exists:**
  - a booking's `status` (unless it is still `idea`) and its `confirmation`;
  - gear `per`;
  - a to-do's `done`;
  - an admin item's `status`.

  A booking marked `booked` is never dropped, even when Claude leaves it out.
- **A booking's `price` is for the whole group** in its own currency. `otherCosts` holds food and local costs that aren't booked; they are counted in the total under "Food & local".
- **`admin` from Claude is keyed by traveller name.** The app maps names to traveller ids, case-insensitively. Unmatched names go under `"group"`.
- **One thread.** The plan chat at the top of Build is the same thread as Setup (`trip.brief`). Every turn gets all three tools. The system prompt says when to use which.

## Review Focus
1. A crafted share link with a hostile `livePlan` (HTML in names, `javascript:` links, bad ids, string numbers) must render as text with no element injected. This is pinned in Task 1 (cleaning) and Task 5 (integration).
2. A full `write_plan` after people have edited must keep `booked` bookings, confirmations, gear cells and done to-dos. This is pinned in Task 1.
3. A night or leg pointing at a booking id that doesn't exist must not crash. The reference becomes `null` (stage 4 will flag it). This is pinned in Task 1.
4. Choosing a second option must not show the first option's plan. Views show a plan only when `livePlan.optionId === trip.chosen`. This is pinned in Task 4.
5. A plan with a price in a currency that has no rate must show the total without it, and name what is missing. This is pinned in Task 2 and Task 5.

**Files:**

- Test: `test/liveplan.test.mjs`

**Interfaces:**
- Consumes: `uid` from `state.js`; the `source`, `https`, `num`, `cur`, `day` and `str` helpers, the `MODES` and `LODGING_TYPES` lists, and `obj`/`S`/`N`/`NN`/`SOURCE`/`MAYBE_SOURCE` from `options.js`. Export those helpers from `options.js` rather than copying them.
- Produces:
  - `WRITE_PLAN_TOOL` and `UPDATE_PLAN_TOOL` (tool definitions, `strict: true`).
  - `normalizePlan(input, trip, { today, optionId, keepIds = false }) -> livePlan`: a fresh clean plan with no merge.
  - `mergePlan(existing, input, trip, { today, partial }) -> { plan, changed: string[] }`. Here `changed` is the list of collection names that were replaced. `partial: true` means only non-null collections are replaced.
  - `liveChoice(trip) -> option | null`.
  - `currentPlan(trip) -> livePlan | null`: the plan only when `livePlan.optionId === trip.chosen`.
  - The constants `BOOKING_STATUSES = ["idea", "decided", "booked", "not-needed"]` and `BOOKING_CATEGORIES = ["transport", "lodging", "permit", "activity", "gear", "other"]`.

The `write_plan` input schema has every property required, with nullable types where marked:
- `days[]`: `{ id, date, move, km?, ascentM?, descentM?, hours?, night: { name, type ∈ LODGING_TYPES ∪ ["none"], bookingId? }, fallback, legs[]: { id, mode ∈ MODES ∪ ["walk"], from, to, time, bookingId?, note }, points[]: { name, lat?, lon?, kind ∈ ["night","start","end","sight","transport"] } }`;
- `bookings[]`: `{ id, what, category ∈ BOOKING_CATEGORIES, pick, alternative, price?, currency, seenOn, status ∈ BOOKING_STATUSES, link?, bookBy?, details, source? }`;
- `permits[]`: `{ id, what, who[] (traveller names or "all"), how, leadTime, bookBy?, note }`;
- `admin[]`: `{ id, traveller, what, note }`;
- `gear[]`: `{ id, name, note }`;
- `food`;
- `todo[]`: `{ id, date?, what }`;
- `otherCosts[]`: `{ id, what, amount, currency, seenOn }`;
- `sources[]` (SOURCE);
- `rates[]`: the same shape as in `OPTIONS_TOOL`.

`UPDATE_PLAN_TOOL` has the same properties, each wrapped as `{ anyOf: [X, { type: "null" }] }`. The tool descriptions say that a booking price is for the whole group, in its own currency, and that the app computes every total.
